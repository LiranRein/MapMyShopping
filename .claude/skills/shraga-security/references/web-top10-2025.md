# OWASP Top 10:2025 - Vibe-Coding Mapping

Baseline version: OWASP Top 10:2025 (owasp.org/Top10/2025/). Last verified: 2026-10-14.
Run the Freshness Protocol before relying on this file for a PRD.

Each item: what it means in an AI-built app (typically Claude Code with Supabase or a similar backend), what to check, and the required control.

---

## A01:2025 - Broken Access Control
**In vibe-coded apps:** tables without RLS or with permissive policies; "admin" pages protected only by hiding the link; IDs in URLs that let one user open another user's record; storage buckets public by default.
**Check:** every table and bucket has an explicit policy; every privileged action is checked on the server; users cannot access records by changing an ID.
**Control:** deny by default; RLS / server-side authorization on every read and write; role checks for admin functions on the server; private buckets with signed URLs.
**Default severity if missing with real data:** Critical.

## A02:2025 - Security Misconfiguration
**In vibe-coded apps:** debug mode or verbose errors in production; default settings left on; CORS open to `*`; email confirmation disabled; leftover test users or seed data.
**Check:** production settings reviewed; error pages do not leak stack traces; CORS limited to own domains; auth settings deliberate.
**Control:** environment-specific config; security headers; minimal exposed endpoints; a pre-launch config checklist.

## A03:2025 - Software Supply Chain Failures
**In vibe-coded apps:** the AI tool adds npm packages freely, including abandoned, typo-squatted or vulnerable ones; unverified MCP servers or templates; no lockfile discipline.
**Check:** list of dependencies added per phase; known advisories for each; source of any MCP server, template or plugin.
**Control:** prefer well-maintained packages; run dependency audit (e.g. `npm audit`) per phase; pin versions; approve new dependencies explicitly in the Plan review.

## A04:2025 - Cryptographic Failures
**In vibe-coded apps:** custom password handling instead of the platform's auth; sensitive data stored in plain text; tokens in localStorage without consideration; HTTP endpoints.
**Check:** passwords handled only by the auth provider; sensitive fields identified; HTTPS everywhere.
**Control:** use the platform's managed auth; encrypt sensitive fields where required; never roll your own crypto; HTTPS only.

## A05:2025 - Injection
**In vibe-coded apps:** raw SQL built from strings in server functions; user content rendered as HTML (`dangerouslySetInnerHTML`); user input concatenated into AI prompts that drive actions (see LLM01).
**Check:** parameterized queries / query builder only; no raw HTML rendering of user content; prompt inputs separated from instructions.
**Control:** server-side validation with a schema (e.g. zod); parameterized queries; output encoding; sanitization for any rich text.

## A06:2025 - Insecure Design
**In vibe-coded apps:** no threat thinking at all; business rules enforced only in UI; no rate limits on expensive or sensitive actions (login, AI calls, invites, password reset).
**Check:** abuse cases written for key flows ("what if a user calls this 10,000 times?"); trust boundaries defined in the PRD.
**Control:** trust boundaries and abuse cases in the PRD; rate limits; business rules on the server; this skill applied from Phase 0.

## A07:2025 - Authentication Failures
**In vibe-coded apps:** custom login logic; no email verification; weak password rules; no protection against brute force; sessions that never expire; magic links that do not expire.
**Check:** auth fully delegated to a managed provider; session lifetime defined; reset flow secure.
**Control:** managed auth (Supabase Auth / Clerk / Auth0 etc.); email verification; rate limiting on auth endpoints; MFA for admins where available.

## A08:2025 - Software or Data Integrity Failures
**In vibe-coded apps:** webhooks (Stripe, etc.) accepted without signature verification; client sends prices or roles that the server trusts; unsigned data imported and trusted.
**Check:** every webhook verifies signatures; prices, roles and permissions are computed on the server.
**Control:** verify webhook signatures; never trust client-supplied amounts or roles; idempotent handlers.

## A09:2025 - Security Logging and Alerting Failures
**In vibe-coded apps:** no logs on server functions; failed logins and permission denials invisible; no alert when AI spend spikes.
**Check:** security-relevant events logged (auth failures, permission denials, admin actions, AI usage); someone gets alerted.
**Control:** structured logging in server functions; audit log table for admin actions; billing and error-rate alerts.

## A10:2025 - Mishandling of Exceptional Conditions
**In vibe-coded apps:** errors swallowed silently; "fail-open" logic (if the permission check errors, allow); unhandled AI or API timeouts leaving data half-written.
**Check:** every external call has error handling; permission checks fail closed; partial writes are rolled back or retried idempotently.
**Control:** fail closed; explicit error states in UI; timeouts and retry caps; transactions for multi-step writes.

## Quick checklist (copy into phase validation)

- [ ] A01 Every table / bucket has explicit access rules enforced on the server
- [ ] A02 Production config reviewed; no verbose errors; CORS restricted
- [ ] A03 New dependencies listed and audited
- [ ] A04 Auth via managed provider; HTTPS; sensitive fields identified
- [ ] A05 Server-side schema validation; no raw SQL or raw HTML from user input
- [ ] A06 Abuse cases and rate limits for expensive / sensitive actions
- [ ] A07 Email verification, session lifetime, brute-force protection
- [ ] A08 Webhook signatures verified; prices and roles computed server-side
- [ ] A09 Security events logged; alerts configured
- [ ] A10 Fail closed; every external call handles errors and timeouts
